# Защита лабораторной работы 1

## Короткое выступление

Для курса мы выбрали ProKitchen — ассистент повара. Это собственный проект Сергея Саламатина, который мы развиваем командой из трёх человек. Сергей отвечает за интерфейс, Олег Ремез — за сервер и базу данных, Гарик Варданян — за тестирование, запуск и документацию.

Приложение помогает повару рассчитывать себестоимость блюд, сохранять их состав и формировать PDF-этикетки. Основные сущности — пользователь, блюдо, ингредиент и аллерген. В системе две технические роли: пользователь работает с блюдами, администратор управляет пользователями и правами.

Клиент написан на React и TypeScript и собирается через Vite. Сервер использует Node.js и Express, основной подтверждённый вариант хранения — SQLite. Браузер обращается к REST API с префиксом /api/v1. Точка запуска сервера — Back/src/server.js; приложение в app.js можно импортировать для тестов без открытия порта.

В первой лабораторной мы зафиксировали исходное состояние проекта, паспорт, карту функций, распределение ответственности и предварительный план на семестр. Существующие решения опубликованной lab-1 сохранили. В проекте уже есть безопасные миграции: выполненные изменения учитываются в журнале с контрольными суммами, повторный запуск сохраняет данные, а ошибка приводит к откату транзакции.

Для запуска закреплены Node.js 22.20.0 и npm 10.9.3. Команда npm run setup устанавливает зависимости по lock-файлам, создаёт локальные настройки и готовит базу. Команда npm run dev запускает интерфейс и API. Проверка npm run check работает на отдельной временной базе и не меняет пользовательские данные.

В репозитории есть серверные тесты, автоматическая проверка API и PDF, сборка клиента и CI. Чистый запуск проверен в Ubuntu через GitHub Actions. Текущие ошибки типов, линтера и старых клиентских тестов, а также вопрос поддержки PostgreSQL оформлены отдельными issues. Мы не объявляем эти части исправленными.

Результат первой работы — проект с воспроизводимым запуском, понятной структурой, зафиксированными проблемами и планом дальнейших лабораторных. Подробные требования и окончательные границы будем уточнять во второй работе.

## Что показать

1. Открыть README, паспорт `docs/00-project.md`, issue product и PR первой лабораторной.
2. Показать `.nvmrc`, команды setup/dev/check и успешную проверку `local-sqlite` в GitHub Actions.
3. Открыть http://127.0.0.1:5173/api/v1/health: ожидаются `status: ok` и `database: ok`.
4. В калькуляторе задать две порции и 200 г картофеля по 0,05 ₽/г. Расчёт: 200 × 0,05 = 10 ₽ за блюдо, 10 / 2 = 5 ₽ за порцию.
5. При необходимости показать сохранённое блюдо и получение PDF, затем issues с известными проблемами.

## Короткие ответы на вопросы

**Зачем первая лабораторная, если приложение уже написано?** Зафиксировать точку отсчёта, обеспечить повторяемый запуск и понять, что и как команда будет развивать в течение семестра.

**Что сделали именно сейчас?** Уточнили готовые материалы первой лабы под команду из трёх человек, проверили комплект, повторно проверили существующий запуск и подготовили сдачу. Уже опубликованные технические исправления не переписывали и не выдаём за новые.

**Где исходники и тесты?** Клиент — Front/src, сервер — Back/src, серверные тесты — Back/tests, клиентские — Front/src/tests, браузерные — Front/tests/e2e. Корневые src и tests содержат указатели на существующую структуру.

**Почему SQLite?** Для базового локального запуска не требуется отдельный сервер БД. Есть адаптер PostgreSQL, но его полноценная поддержка пока не подтверждена; это вопрос отдельного issue.

**Как проверяется расчёт?** Есть модульные тесты сервиса и контрольный пример с известными количествами и ценами. Сценарий check дополнительно проверяет HTTP API и PDF на временной базе.

**Все ли тесты проходят?** Серверный набор проверяется в CI. Проверка типов, линтер и устаревшие тесты клиента имеют известные ошибки; успешная сборка Vite их не отменяет. Они оформлены в issues #2 и #3.

**Почему ошибки ещё открыты?** Первая работа требует выявить и зафиксировать проблемы и обеспечить основной запуск. Исправление всех ошибок приложения не является условием этой работы.

**Как защищены пароли и доступ?** Пароли хранятся в виде bcrypt-хешей, API использует JWT, сервер проверяет роль и владельца объекта. Конфигурация с локальными секретами хранится в игнорируемом Back/.env.

**Нужен ли ключ внешнего API?** Только для дополнительной пищевой ценности через Spoonacular. Расчёт себестоимости работает без него.

**Почему issue product открыт?** Он закрывается после фактического согласования проекта и плана преподавателем. Подготовленная документация и успешный CI не заменяют это согласование.
