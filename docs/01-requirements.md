# ProKitchen — описание проекта и требования

Версия документа: **1.0**. Дата: **26 октября 2026 года**. Автор: **Саламатин Сергей (gWalut)**. Статус: на ревью.

Здесь описаны возможности ProKitchen, требования на семестр, пользовательские сценарии и модели системы. Документ составлен по коду Front/Back и результатам проверки приложения. Номера FR, NFR и US будут использоваться в следующих лабораторных.

## 1. О приложении

### 1.1. Назначение и пользователи

ProKitchen помогает повару рассчитать стоимость состава блюда, сохранить личную рецептуру и скачать PDF-этикетку. Приложение объединяет расчёты, рецептуры и сведения об аллергенах, которые иначе приходится вести вручную.

В приложении две роли: пользователь (`user`) и администратор (`admin`). Пользователь регистрируется и входит в приложение, рассчитывает себестоимость, работает со своими блюдами и формирует этикетки. Администратор дополнительно просматривает пользователей и изменяет их роли. Личные блюда доступны владельцу; управление чужими личными блюдами администратором в объём работы не входит.

Основной объём семестра: FR-1–FR-5 и FR-8. Дополнительный: FR-6–FR-7. FR-9 отложено. Полная складская система, кассы, закупки, восстановление пароля по почте, производственный хостинг и подтверждённая поддержка PostgreSQL в этот объём не входят. Объём работ нужно согласовать с преподавателем.

### 1.2. Термины

| Термин | Значение в ProKitchen |
| --- | --- |
| Пользователь | Учётная запись с email, хешем пароля и ролью user/admin; таблица `users`. |
| Пользовательское блюдо | Личная рецептура из калькулятора: название, число порций, состав и стоимости; `custom_dishes`. |
| Позиция состава | Снимок названия продукта, количества, единицы и цены внутри `ingredients_json` пользовательского блюда; отдельной SQL-таблицы нет. |
| Блюдо каталога | Отдельная рецептура в `dishes`, связанная с ингредиентами через `dish_ingredients`; не тождественна пользовательскому блюду. |
| Ингредиент | Запись справочника `ingredients` с названием, единицей и ценой за единицу; может быть связан с аллергенами. |
| Аллерген | Справочная характеристика продукта из `allergens`; связь с ингредиентом — `ingredient_allergens`. |
| Себестоимость | Сумма произведений количества каждой позиции на её цену. Цена задана в ₽ за указанную единицу: г, мл или шт. Это стоимость состава, без наценки, труда и накладных расходов. |
| Порция | Одна из N равных частей введённого состава. Для калькулятора N меняет стоимость порции, а не массу введённых ингредиентов. |
| Этикетка | Выходной PDF с названием, весом, порциями, названиями ингредиентов и датами; не запись таблицы `labels`, которая содержит теги каталога. |
| Избранное | Экран `/favorites` сейчас показывает личные `custom_dishes`; удаление на нём удаляет личное блюдо. Отдельное API избранного каталога использует общий список `user_id = 0`; оно не является личным списком. |

### 1.3. Что уже реализовано и проверено

Клиент — React/TypeScript/Vite, сервер — Express/Node.js, основной локальный режим — SQLite. Есть регистрация и вход, калькулятор, личные блюда, PDF, поиск каталожных блюд для матрицы аллергенов, API справочника ингредиентов и экран администрирования. Питательная ценность использует необязательный Spoonacular API. Каталог продуктов калькулятора сейчас задан в клиентском коде и не синхронизируется со справочником БД.

26.10.2026 на Windows с Node.js 22.20.0 и npm 10.9.3 выполнены проверки:

- `npm run check` прошёл: новая временная БД, повторные миграции, health, регистрация, вход, отказ без токена, отказ user в администрировании, сохранение/чтение блюда и сигнатура PDF.
- `npm run build` прошёл. Сборка Vite не подтверждает отсутствие ошибок TypeScript и ESLint.
- Запуск Jest на этой локальной копии обнаружил **25 тестов в 5 наборах**, все прошли, в том числе после `--no-cache`. В отчёте первой лабораторной указаны 32 теста в 6 наборах. Причину расхождения нужно выяснить.
- Клиент и API запущены с отдельной временной SQLite-базой. В браузере подтверждены исходный расчёт 200 × 0,05 = 10 ₽, 2 порции по 5 ₽ и недоступность необязательного виджета питания без ключа. После смены 2 порций на 4 при прежних 200 г интерфейс показал 20 ₽ и 5 ₽: это дефект FR-2, ожидается 10 ₽ и 2,50 ₽.

Проверка охватывала основные сценарии. Для остальных требований нужны дополнительные тесты. ## 2. Требования к функционалу

### 2.1. Функциональные требования

Приоритеты: **обязательно в этом семестре**, **желательно**, **потом**. Состояния: **уже есть**, **нужно доработать**, **нужно сделать**. Для готовых функций также указан результат проверки.

| Номер | Требование | Приоритет | Состояние | Признак выполнения |
| --- | --- | --- | --- | --- |
| FR-1 | Пользователь может зарегистрировать учётную запись и войти с email и паролем. | Обязательно в этом семестре | Уже есть | При новом email, пароле от 8 символов, совпадающем подтверждении и принятой политике создаётся user; вход открывает защищённые функции, неверный пароль не даёт доступа. |
| FR-2 | Пользователь может рассчитать общую себестоимость введённого состава и стоимость одной порции. | Обязательно в этом семестре | Нужно доработать | При N ≥ 1 целом и непустом составе сумма равна Σ(qᵢ × pᵢ), стоимость порции равна сумме/N; изменение N сохраняет общую стоимость при прежнем составе; отрицательные/нечисловые данные отклоняются, деньги выводятся с двумя знаками. |
| FR-3 | Пользователь может сохранить рассчитанное блюдо в свой личный список. | Обязательно в этом семестре | Нужно доработать | Название, состав, N и согласованные стоимости сохраняются у владельца и читаются после перезагрузки; нулевая цена допустима; сервер отклоняет подменённые итоги и не создаёт запись. |
| FR-4 | Пользователь может найти, просмотреть, изменить и удалить своё сохранённое блюдо. | Обязательно в этом семестре | Нужно доработать | Поиск возвращает свои совпадения; изменение состава/N пересчитывает итоги по FR-2; удалённое блюдо отсутствует в списке и возвращает 404 при чтении; чужие данные недоступны. |
| FR-5 | Пользователь может скачать PDF-этикетку своего сохранённого блюда по весу, дате изготовления и сроку годности в днях. | Обязательно в этом семестре | Уже есть | Для корректных целых веса ≥ 1 г и срока ≥ 1 дня получается открываемый PDF с названием, общим весом, N, округлённым весом порции, составом и обеими датами; пример US-5 содержит точные значения; неполные параметры не создают PDF. |
| FR-6 | Пользователь может найти блюдо каталога по названию и увидеть связанные с его ингредиентами аллергены. | Желательно | Нужно доработать | Для подготовленного каталожного блюда показываются уникальные аллергены его ингредиентов; для неизвестного названия — сообщение об отсутствии; пустой каталог объясняется пользователю без ложного утверждения об отсутствии аллергенов. |
| FR-7 | Пользователь может вести справочник ингредиентов с единицами и ценами и использовать его при составлении блюда. | Желательно | Нужно доработать | Через интерфейс доступны создание и изменение ингредиента; новый выбор в калькуляторе получает актуальную единицу/цену из БД; старый сохранённый снимок состава не меняется автоматически. |
| FR-8 | Администратор может просматривать список пользователей и изменять роль выбранной учётной записи между user и admin. | Обязательно в этом семестре | Уже есть | Admin видит список и сохраняет допустимую роль; после нового входа выбранная учётная запись получает соответствующий доступ; обычный user получает 403 на эти операции. |
| FR-9 | Пользователь может вести собственное избранное из блюд каталога независимо от других пользователей. | Потом | Нужно сделать | Два пользователя добавляют/удаляют каталожные блюда без изменения списка друг друга; личные рецептуры остаются отдельными объектами; удаление отметки не удаляет рецептуру. |

FR-2–FR-4 описывают целевое согласованное поведение. Сейчас `handlePortionsChange` меняет общую сумму иначе, чем повторный `calculate`; API личного блюда принимает присланные клиентом итоги без пересчёта, а проверка `if (!total_cost)` отклоняет допустимый ноль. Исправление этих ошибок запланировано на этап разработки. В FR-6 используются связи каталога; определение аллергенов по свободному тексту личного блюда пока не предусмотрено. FR-7 имеет серверное API, но отдельного интерфейса справочника и его подключения к калькулятору нет. FR-9 требует изменения существующей общей модели избранного и нового интерфейса.

## 3. Пользовательские сценарии

### US-1. Регистрация и вход — FR-1

Я как новый пользователь имею email, пароль от 8 символов, его подтверждение и согласие с политикой; открываю регистрацию, заполняю поля, отправляю форму и затем вхожу с этими email/паролем; получаю учётную запись user и доступ к личным блюдам.

**Вход:** свободный email, пароль/подтверждение, согласие. **Выход:** запись пользователя и действующая сессия; пароль в ответе отсутствует. Неверный пароль не открывает защищённый список; повторный email не создаёт вторую запись.

### US-2. Расчёт стоимости — FR-2, ключевой

Я как пользователь имею действующую сессию, название блюда, позиции состава, цены и число порций; открываю калькулятор, ввожу название, добавляю позиции, задаю N и нажимаю «Рассчитать»; получаю общую себестоимость и стоимость порции.

**Вход:** сессия пользователя, «Картофель тест», картофель 200 г по 0,05 ₽/г, N = 2. **Выход:** строка 10,00 ₽, итог 10,00 ₽, порция 5,00 ₽; БД не меняется. Затем меняю N на 4 при прежнем составе: целевой результат — итог 10,00 ₽ и порция 2,50 ₽. Эта последняя часть пока не выполнена: текущий интерфейс показывает 20,00 ₽ и 5,00 ₽.

**Ошибка:** при пустом названии и заполненном составе нажатие «Рассчитать» показывает существующее сообщение «Введите название блюда», новый результат не вычисляется. Для отрицательного количества/цены или дробного N целевое сообщение: «Проверьте количество, цену и число порций»; недопустимый расчёт не показывается и не сохраняется. Такую проверку ещё нужно добавить.

### US-3. Сохранение расчёта — FR-3, ключевой

Я как вошедший пользователь имею корректный рассчитанный состав; нажимаю звезду сохранения, затем открываю «Избранное» и перезагружаю страницу; получаю своё блюдо с теми же данными.

**Вход:** сессия A, «Картофель тест», N = 2, позиция `{name: "Картофель", weight: 200, unit: "г", pricePerUnit: 0.05}`, `total_cost = 10`, `cost_per_portion = 5`. **Выход:** одна новая запись, принадлежащая A, с этими значениями; API создания возвращает 201 и новый id. В интерфейсе существующее сообщение — «Блюдо сохранено в избранное!»; экран представляет личные блюда, а не общее избранное каталога.

**Ошибка:** если название или состав пусты, интерфейс показывает существующее «Введите название блюда и добавьте ингредиенты» и не отправляет сохранение. Прямой API-запрос с пустым `ingredients` возвращает 400, `message: "Ошибка валидации"`, деталь поля `ingredients`; запись не создаётся. При подмене итоговой суммы на 1 ₽ вместо 10 ₽ целевое поведение — 400 с сообщением «Стоимость не соответствует составу», без записи; сейчас сервер этому условию не соответствует. Нулевая корректная стоимость должна сохраняться после доработки.

### US-4. Работа с личным блюдом — FR-4

Я как пользователь имею ранее сохранённое своё блюдо; открываю «Избранное», выбираю карточку, изменяю состав или число порций и сохраняю; получаю обновлённую рецептуру, затем удаляю её и получаю список без неё.

**Вход:** сессия владельца, id своего блюда, новые позиции/N. **Шаги:** открыть список → найти нужную карточку → изменить → сохранить → перечитать → удалить → перечитать список. **Выход:** значения и итоги согласованы с FR-2; после удаления чтение id даёт 404. Поиск по имени/описанию должен быть доступен пользователю; API `GET /custom-dishes?search=...` уже есть, наличие полного удобного поиска в интерфейсе требует доработки. Сессия B не получает содержимое блюда A и не изменяет его.

### US-5. Получение этикетки — FR-5, ключевой

Я как владелец имею сохранённое блюдо; открываю «Печать этикеток», выбираю своё блюдо, задаю вес, дату и срок в днях, нажимаю «Напечатать»; получаю скачанный PDF, который можно открыть и напечатать.

**Вход:** блюдо «Картофель тест», 2 порции, состав «Картофель»; общий вес 200 г, изготовление 2026-10-26, срок 2 дня. **Выход:** PDF с заголовком «КАРТОФЕЛЬ ТЕСТ», общим весом 200 г, 2 порциями, весом порции 100 г, составом «Картофель», датой изготовления 26.10.2026 и датой «Годен до» 28.10.2026. Ответ API — 200, `Content-Type: application/pdf`, начало файла `%PDF-`. Клиент предлагает имя `Этикетка_Картофель тест_2026-10-26.pdf`. Блюдо не изменяется; запись этикетки в БД не создаётся.

**Ошибка:** при выбранном блюде и пустом весе интерфейс показывает существующее «Заполните все поля!» и не скачивает PDF. Прямой запрос `GET /custom-dishes/{id}/label?manufactureDate=2026-10-26&shelfLife=2` без веса получает 400, `message: "Ошибка валидации"`, деталь `weight`; PDF не формируется. Для чужого существующего блюда с полными корректными параметрами — 403 и `message: "Access denied"`.

Дата годности вычисляется прибавлением введённого числа календарных дней; срок задаёт пользователь. Аллергены и пищевая ценность в PDF не выводятся. Для длинного состава и нескольких страниц нужна отдельная проверка.

### US-6. Проверка аллергенов каталога — FR-6

Я как пользователь имею действующую сессию, точное название блюда каталога и подготовленные связи его ингредиентов с аллергенами; открываю матрицу, ввожу название и запускаю поиск; получаю найденное блюдо и набор его аллергенов.

**Вход:** сессия пользователя, название существующего `dishes`, связанные `ingredients` и `allergens`. **Выход:** найденное название и уникальный набор аллергенов; записи не изменяются. Для неизвестного названия показывается «Блюдо \"…\" не найдено». Свободный текст личного состава не связывается со справочником автоматически. Пустая БД не считается доказательством работы заполненной матрицы.

### US-7. Использование справочника — FR-7

Я как пользователь имею название ингредиента, единицу и цену; открываю будущий экран справочника, создаю или исправляю запись, затем выбираю её в калькуляторе; получаю позицию с актуальной ценой.

**Вход:** сессия user, «Картофель», г, 0,05 ₽/г. **Выход:** запись справочника и новая позиция расчёта; ранее сохранённые снимки состава не меняются. API создания/изменения уже есть, экран и связь с калькулятором планируются. Отрицательная цена не сохраняется, форма объясняет ошибку.

### US-8. Управление ролями — FR-8

Я как администратор имею действующую сессию и id существующей учётной записи; открываю пользователей, выбираю запись, меняю user на admin и сохраняю; получаю обновлённую роль, а выбранный пользователь после повторного входа получает административный доступ.

**Вход:** сессия admin, id другого тестового пользователя, роль user/admin. **Выход:** изменённая роль и список без хешей паролей. Проверка из сессии обычного user возвращает 403 и не меняет роль. Выдача самого первого admin выполняется отдельно при настройке; регистрация не должна позволять выбирать admin. Мгновенный отзыв прав ранее выданного JWT не заявляется этим сценарием.

### US-9. Личное избранное каталога — FR-9

Я как пользователь A имею выбранное блюдо каталога; нажимаю добавление в личное избранное и открываю будущий отдельный список; получаю только свои отметки, затем удаляю отметку без удаления блюда.

**Вход:** сессии A/B, id каталожного блюда. **Выход:** отметка есть у A и отсутствует у B; после снятия отметки рецептура существует. Сценарий отложен: текущее API использует общий `user_id = 0`, а `/favorites` показывает личные рецептуры.

Модель данных включает **Пользователя**, **Пользовательское блюдо**, **Блюдо каталога**, **Ингредиент**, **Аллерген** — ровно пять сущностей из словаря. Массив позиций состава показан атрибутом пользовательского блюда: он хранит снимки, а не гарантированные внешние ключи справочника. Таблицы связей показаны подписями отношений. Таблицы избранного, токенов и журналов в эту упрощённую модель не включены.

Диаграмма состояний моделирует пользовательский процесс: черновик и расчёт живут в клиенте, сохранённый объект — в `custom_dishes`. В БД нет поля `status`, состояний публикации или производственного заказа. Скачивание PDF не меняет блюдо. После изменения состава старый расчёт должен сбрасываться; этот переход ещё нужно доработать по FR-2–FR-4.

Необязательный Spoonacular показан в контексте как существующая интеграция питания; отдельного FR на него в объёме семестра нет. SQLite входит внутрь границы системы. Пользователь печатает скачанный PDF самостоятельно.
